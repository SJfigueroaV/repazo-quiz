4.1 Stack, Heap y referencias compartidas

En esta sección

  • Pones nombre a los dos lugares de la memoria que ya dibujaste en la Parte 1.
  • Entiendes por qué cambiar un objeto que sacaste con get cambia el de la lista…
  • …y por qué con un Integer o un Double eso no pasa.

En la sección 1.2 dibujamos una variable apuntando a un arreglo y el arreglo apuntando a objetos. Esos dos lados del dibujo tienen nombre:

  • El Stack (pila) guarda las variables locales de cada método que se está ejecutando: int, double, boolean… y las referencias. Es pequeño y se limpia solo: cuando un método termina, sus variables desaparecen.
  • El Heap (montículo) guarda todos los objetos: cada cosa creada con new, incluidos los arreglos y las listas. Ahí los objetos viven mientras alguien los apunte; cuando nadie los apunta, el recolector de basura (Garbage Collector) los borra.

Por eso new Cliente[3] hace una sola cosa en el Heap (el arreglo de 3 referencias en null) y cada new Cliente(...) hace otra. Son dos instanciaciones distintas: primero el estante, después cada objeto.

Ahora la consecuencia que más se usa en la práctica. Este programa saca un cliente de la lista, lo cambia, y vuelve a mirar la lista:

Alias.java
List<Cliente> cartera = new ArrayList<>();
cartera.add(new Cliente("101", "Carlos", 1500000.0));
cartera.add(new Cliente("102", "Diana", 2400000.0));

Cliente c = cartera.get(1);        // c apunta al MISMO objeto que la casilla 1
c.setCupo(3000000.0);              // lo cambio a través de c...

System.out.println("Cupo leído desde la lista: " + cartera.get(1).getCupo());
System.out.println("¿Es el mismo objeto? " + (c == cartera.get(1)));

salida

Cupo leído desde la lista: 3000000.0 ¿Es el mismo objeto? true

get no te entrega una copia del cliente: te entrega otra referencia al mismo objeto. A eso se le llama alias. Así se ve la memoria:

STACK (main) HEAP cartera --------> ArrayList (size = 2) elementData --> [ 0x01 | 0x02 | null | ... ] | | v v +---------+ +---------+ | Carlos | | Diana | | 1500000 | | 3000000 | +---------+ +---------+ ^ c ------------------------------------------------+

Hay un solo objeto Diana, con dos flechas que llegan a él. Cambiarlo por cualquiera de las dos es cambiarlo. Por eso, para actualizar un objeto de la lista, no hace falta set: lo buscas, llamas a su setter, y listo. set(i, otro) es para reemplazar el objeto de la casilla por uno distinto.

La excepción: las envolventes no se pueden modificar

Con una lista de números la historia cambia. Mira:

Envolventes.java
List<Integer> puntos = new ArrayList<>();
puntos.add(10);
puntos.add(20);

for (Integer p : puntos) {
    p = p + 5;                     // cambia la variable p, no la lista
}
System.out.println("Con for-each: " + puntos);

for (int i = 0; i < puntos.size(); i++) {
    puntos.set(i, puntos.get(i) + 5);   // reemplaza la casilla
}
System.out.println("Con set:      " + puntos);

salida

Con for-each: [10, 20] Con set: [15, 25]

Integer, Double, String y compañía son inmutables: no tienen setters, ningún método los cambia por dentro. p + 5 crea un Integer nuevo, y p = ... solo mueve la flecha de la variable p hacia él. La casilla de la lista sigue apuntando al viejo. Para cambiar lo que guarda la lista, tienes que poner el nuevo en la casilla, con set.

La regla

Objeto con setters (Cliente, Producto): lo buscas y lo cambias, la lista lo ve. Objeto inmutable (Integer, Double, String): no se puede cambiar, solo reemplazar con set(i, nuevo). Asignar a la variable del for-each nunca cambia la lista.

Pregunta rápida

Tienes List<Producto> lista con un producto de precio 100. Ejecutas Producto p = lista.get(0); p = new Producto("X", 500);. ¿Qué precio tiene ahora lista.get(0)?

Asignar a una variable nunca toca el objeto al que apuntaba antes: solo cambia hacia dónde apunta la variable. La casilla 0 sigue con su producto de 100. Otra cosa sería p.setPrecio(500), que sí cambia el objeto compartido.

4.2 El iterador: lo que hay debajo del for-each

En esta sección

  • Ves en qué se convierte un for-each cuando se compila.
  • Eliminas con it.remove() sin provocar ConcurrentModificationException.
  • Eliges entre for hacia atrás, Iterator y removeIf.

En la sección 2.4 dijimos que un for-each "le pide un iterador a la lista". Es literal: el compilador convierte el primer bloque en el segundo.

// lo que escribes
for (String codigo : codigos) {
    System.out.println(codigo);
}

// lo que Java ejecuta
Iterator<String> it = codigos.iterator();
while (it.hasNext()) {
    String codigo = it.next();
    System.out.println(codigo);
}

Un Iterator es un objeto que sabe recorrer una colección, y tiene tres métodos:

MétodoQué hace
it.hasNext()¿Queda algún elemento por visitar?
it.next()Avanza y devuelve el siguiente elemento.
it.remove()Elimina de la lista el último elemento que devolvió next().

El for-each esconde el iterador, y con él el único remove seguro. Si escribes el iterador a mano, lo tienes disponible:

ConIterador.java
List<String> codigos = new ArrayList<>();
codigos.add("CTA-01");
codigos.add("CTA-02");
codigos.add("CTA-03");

Iterator<String> it = codigos.iterator();   // import java.util.Iterator;
while (it.hasNext()) {
    String codigo = it.next();
    if (codigo.equals("CTA-02")) {
        it.remove();               // borra el último que devolvió next()
    }
}
System.out.println(codigos);

salida

[CTA-01, CTA-03]

¿Por qué este remove sí funciona y codigos.remove(codigo) no? Recuerda el contador de modificaciones de la sección 2.4: la lista lleva la cuenta, y el iterador guarda una copia para detectar cambios hechos a sus espaldas. it.remove() borra y actualiza su copia, así que los números siguen coincidiendo. Además acomoda su posición interna para no saltarse el elemento que se corrió a la izquierda.

Tiene una sola regla: remove() borra lo que devolvió el último next(), así que hay que llamar next() antes, y no se puede llamar remove() dos veces seguidas. Si no:

DobleRemove.java
Iterator<String> it = codigos.iterator();
it.remove();                       // todavía no has llamado next()

salida

Exception in thread "main" java.lang.IllegalStateException at java.base/java.util.ArrayList$Itr.remove(ArrayList.java:1071) at DobleRemove.main(DobleRemove.java:9)

¿Cuál de las tres formas uso?

FormaCuándo
lista.removeIf(x -> ...)Solo quieres borrar los que cumplen una condición. Es la más corta y la primera opción.
Iterator + it.remove()Además de borrar, tienes que hacer algo con cada eliminado: guardarlo, contarlo, registrarlo en un historial.
for hacia atrásNecesitas el índice de cada elemento. Funciona, pero es el más fácil de escribir mal.

Pregunta rápida

Dentro del while de ConIterador, cambias it.remove() por codigos.remove(codigo). ¿Qué pasa?

Escribir el iterador a mano no lo vuelve seguro: lo seguro es borrar a través de él. Si borras directo en la lista, el iterador ve que el contador de modificaciones cambió sin su permiso, igual que en un for-each. (Con estos datos en concreto el bucle termina sin excepción y sin revisar CTA-03: es el caso del penúltimo, el de la sección 2.4.)

4.3 Una lista, muchos tipos: interfaces y polimorfismo

En esta sección

  • Escribes una interfaz y dos clases que la implementan.
  • Guardas objetos de las dos clases en una sola List.
  • Entiendes quién decide qué método se ejecuta: la variable o el objeto.

Hasta ahora cada lista guardaba una sola clase: List<Cliente>, List<Producto>. Pero un carrito de compras real mezcla cosas muy distintas: un servicio de hosting se cobra por meses, un router se cobra por precio más envío según el peso. No se calculan igual y no tienen los mismos atributos. ¿Una lista para cada tipo? Entonces cada suma, cada recorrido y cada impresión habría que escribirlos dos veces, y una tercera vez cuando llegue el tercer tipo.

La salida es preguntarse qué tienen en común. Para el carrito, las dos cosas son facturables: tienen un detalle que imprimir y un importe que cobrar. Eso se escribe como una interfaz:

Facturable.java
public interface Facturable {
    String getDetalle();
    double calcularImporte();
}

Una interfaz es un contrato: lista qué métodos hay, sin decir cómo se hacen (no tienen cuerpo, solo punto y coma). Cada clase que implements Facturable se compromete a escribirlos, cada una a su manera:

public class ServicioDigital implements Facturable {
    private String nombre;
    private double costoMensual;
    private int meses;

    // constructor...

    @Override
    public String getDetalle() {
        return nombre + " [" + meses + " meses]";
    }

    @Override
    public double calcularImporte() {
        return costoMensual * meses;
    }
}

public class ProductoFisico implements Facturable {
    private String descripcion;
    private double precio;
    private double pesoKg;

    // constructor...

    @Override
    public String getDetalle() {
        return descripcion + " (" + pesoKg + " kg)";
    }

    @Override
    public double calcularImporte() {
        double envio = pesoKg > 1.0 ? 25000.0 : 10000.0;
        return precio + envio;
    }
}

Y ahora sí, una sola lista para los dos:

CarritoDemo.java
List<Facturable> carrito = new ArrayList<>();
carrito.add(new ServicioDigital("Hosting web", 45000.0, 6));
carrito.add(new ProductoFisico("Router WiFi", 180000.0, 0.8));
carrito.add(new ProductoFisico("Impresora láser", 650000.0, 7.5));

double total = 0;
for (Facturable item : carrito) {
    System.out.println(item.getDetalle() + " -> " + item.calcularImporte());
    total += item.calcularImporte();
}
System.out.println("Total: " + total);

salida

Hosting web [6 meses] -> 270000.0 Router WiFi (0.8 kg) -> 190000.0 Impresora láser (7.5 kg) -> 675000.0 Total: 1135000.0

Fíjate en el for: la misma línea item.calcularImporte() hizo una multiplicación la primera vuelta y una suma con envío las otras dos. El bucle no sabe ni le importa qué clase es cada ítem: le pregunta al objeto y el objeto responde con su versión. Eso es el polimorfismo ("muchas formas"): una misma llamada, un comportamiento distinto según el objeto.

La variable decide qué puedes pedir; el objeto decide qué se ejecuta

Esta es la regla que ordena todo, y el compilador la hace cumplir. El tipo de la variable (Facturable) decide qué métodos puedes llamar. El objeto real (un ProductoFisico) decide qué código corre. Si pides algo que no está en el contrato, no compila, aunque el objeto lo tenga:

List<Facturable> carrito = new ArrayList<>();
carrito.add(new Regalo());         // Regalo tiene un método getPeso()...
carrito.get(0).getPeso();          // ...pero Facturable no

salida del compilador

SoloContrato.java:7: error: cannot find symbol carrito.get(0).getPeso(); ^ symbol: method getPeso() location: interface Facturable

Los otros dos errores que vas a ver seguro, con su traducción:

ErrorQué significa
Facturable is abstract; cannot be instantiatedEscribiste new Facturable(). Una interfaz es solo un contrato: no se pueden crear objetos de ella, solo de las clases que la implementan.
Regalo is not abstract and does not override abstract method calcularImporte() in FacturableDijiste implements Facturable pero te faltó escribir uno de los métodos del contrato. Ese mensaje te dice cuál.

¿Facturable o IFacturable?

En algunos materiales verás las interfaces con una I delante (IFacturable). Es una costumbre de C#. En Java lo normal es nombrarlas sin prefijo, como las de la propia biblioteca: List, Comparable, Iterator. Las dos compilan igual.

Pregunta rápida

Con Facturable f = new ServicioDigital("Hosting", 45000.0, 6);, ¿qué método se ejecuta en f.calcularImporte()?

La interfaz no tiene código que ejecutar, solo la firma. Compila porque calcularImporte está en el contrato de Facturable, y al ejecutarse corre la versión del objeto real, que es un ServicioDigital: 45.000 × 6.

4.4 Agregar un tipo sin tocar el carrito

En esta sección

  • Compruebas el premio del polimorfismo: tipos nuevos sin editar el código que ya funciona.
  • Reconoces el antipatrón del instanceof en cadena.
  • Filtras una lista polimórfica usando solo el contrato.

Imagina que el carrito del ejercicio 4.6 no usara una interfaz y preguntara por la clase de cada ítem:

// Así NO
for (Object item : items) {
    if (item instanceof ServicioDigital) {
        total += ((ServicioDigital) item).getCostoMensual() * ((ServicioDigital) item).getMeses();
    } else if (item instanceof ProductoFisico) {
        total += ((ProductoFisico) item).getPrecio() + ...;
    }
    // ¿y el tipo que llegue el mes que viene?
}

Cada tipo nuevo obliga a abrir el carrito y agregar otro else if, en total, en masCaro, en la impresión… y un olvido en cualquiera de ellos es un error silencioso. Con la interfaz, un tipo nuevo es una clase nueva y ya: el carrito no se toca. Esta idea tiene nombre, principio abierto/cerrado: el código queda abierto a extenderse (clases nuevas) y cerrado a modificarse (lo que ya funciona no se edita).

Cuándo sí es razonable instanceof

No está prohibido: a veces de verdad necesitas algo que solo tiene una clase (por ejemplo, listar solo los servicios para avisar que se van a renovar). Pero si te ves escribiendo el mismo if/else if por tipos en varios métodos, lo que falta es un método en la interfaz.

Filtrar también se hace a través del contrato. Este método sirve para cualquier Facturable que exista hoy o que se invente mañana, porque lo único que pregunta es el importe:

public List<Facturable> itemsDesde(double minimo) {
    List<Facturable> resultado = new ArrayList<>();
    for (Facturable item : items) {
        if (item.calcularImporte() >= minimo) {
            resultado.add(item);
        }
    }
    return resultado;
}

4.5 Listas que nadie puede cambiar

En esta sección

  • Creas listas inmutables con List.of y List.copyOf.
  • Distingues copia, vista de solo lectura y copia inmutable, y sabes cuál ve los cambios futuros.
  • Proteges una clase de lo que entra, no solo de lo que sale.

Cuando los datos no van a cambiar nunca (los días de la semana, los medios de pago aceptados), Java 9 trae una forma corta de crear la lista:

ListOf.java
List<String> dias = List.of("lunes", "martes", "miércoles");
System.out.println(dias + ", tamaño " + dias.size());
dias.set(0, "domingo");

salida

[lunes, martes, miércoles], tamaño 3 Exception in thread "main" java.lang.UnsupportedOperationException at java.base/java.util.ImmutableCollections.uoe(ImmutableCollections.java:145) at java.base/java.util.ImmutableCollections$AbstractImmutableList.set(ImmutableCollections.java:267) at ListOf.main(ListOf.java:7)

Una lista de List.of es inmutable: add, remove, set y clear lanzan UnsupportedOperationException. Tampoco acepta null: List.of("Ana", null) lanza NullPointerException en el acto. Si necesitas una lista que empiece con esos datos y después cambie, envuélvela: new ArrayList<>(List.of(...)).

En la sección 3.1 viste dos formas de entregar una lista sin que se la roben. Con List.copyOf (Java 10) son tres, y se comportan distinto cuando el dueño cambia su lista después:

Inmutables.java
List<String> original = new ArrayList<>(List.of("pan", "leche"));

List<String> copia = new ArrayList<>(original);
List<String> vista = Collections.unmodifiableList(original);
List<String> congelada = List.copyOf(original);

original.add("café");              // el dueño cambia su lista

System.out.println("original:  " + original);
System.out.println("copia:     " + copia);
System.out.println("vista:     " + vista);
System.out.println("congelada: " + congelada);

try {
    congelada.add("azúcar");
} catch (UnsupportedOperationException e) {
    System.out.println("congelada.add -> UnsupportedOperationException");
}

salida

original: [pan, leche, café] copia: [pan, leche] vista: [pan, leche, café] congelada: [pan, leche] congelada.add -> UnsupportedOperationException
Forma¿Se puede modificar?¿Ve los cambios del original?
new ArrayList<>(x)Sí (es otra lista)No
Collections.unmodifiableList(x)NoSí: es una ventana al original
List.copyOf(x)NoNo: es una foto
List.of(a, b, c)NoNo hay original

La fuga de entrada

En la 3.1 cerramos la fuga de salida: el getter que regala la lista interna. Hay otra, igual de peligrosa, en la entrada:

public Pedido(String codigo, List<Articulo> articulos) {
    this.articulos = articulos;    // guarda la MISMA lista que le pasaron
}

Quien creó el pedido todavía tiene una referencia a esa lista. Si después le agrega un artículo, se lo agrega al pedido, que ya estaba confirmado y cobrado. Es el alias de la sección 4.1 otra vez. La cura es la misma que a la salida: guardar una copia (new ArrayList<>(articulos) o List.copyOf(articulos)). A esto se le llama copia defensiva.

La copia es de la lista, no de los objetos

Todas estas formas copian las referencias, no los objetos: la copia y el original apuntan a los mismos artículos. Si Articulo tuviera setters, alguien podría seguir cambiándolos. Por eso los objetos que viajan en colecciones compartidas suelen ser inmutables: atributos privados y sin setters.

Pregunta rápida

Una clase guarda this.items = Collections.unmodifiableList(items); en su constructor. ¿Está protegida?

Nadie puede modificarla a través de la vista, pero el llamador conserva la lista original y puede agregarle cosas, y la vista las mostrará. Para la entrada hace falta una copia: List.copyOf(items) resuelve las dos fugas de un golpe.

4.6 Imprimir bonito: printf y String.format

En esta sección

  • Controlas decimales, separador de miles y ancho de columna.
  • Sabes por qué el mismo programa imprime 45.000,00 en un computador y 45,000.00 en otro.

Concatenar con + imprime 1135000.0. Una factura necesita 1.135.000,00, y columnas alineadas. Para eso está printf: un texto con especificadores (lo que empieza con %) que se reemplazan, en orden, por los valores que vienen después.

Formato.java
String nombre = "Teclado USB";
int unidades = 3;
double precio = 45000.0;

System.out.printf("%s x %d = %.2f%n", nombre, unidades, unidades * precio);
System.out.printf("[%-15s] [%15s]%n", nombre, nombre);
System.out.printf("$%,.2f%n", 1234567.891);
System.out.printf("$%,12.2f|%n", precio);

String linea = String.format("%-15s | $%,10.2f", nombre, precio);
System.out.println(linea);

salida (en un computador configurado en español de Colombia)

Teclado USB x 3 = 135000,00 [Teclado USB ] [ Teclado USB] $1.234.567,89 $ 45.000,00| Teclado USB | $ 45.000,00
EspecificadorQué haceEjemplo
%sTexto (o cualquier objeto, con su toString)Teclado USB
%dEntero3
%.2fDecimal con 2 cifras, redondeado135000,00
%,.2fIgual, con separador de miles1.234.567,89
%15sOcupa 15 caracteres, alineado a la derecha    Teclado USB

%,12.2fNúmero de 12 caracteres, a la derecha: ideal para columnas de plata   45.000,00

printf imprime; String.format, con exactamente la misma sintaxis, devuelve el texto. Casi siempre conviene el segundo dentro de las clases: un método que devuelve un String se puede probar, guardar en un archivo o mostrar en una ventana, y uno que imprime solo sirve para la consola.

Punto o coma: depende del computador

El separador de miles y el decimal los decide la configuración regional (Locale) de la máquina. El mismo programa en un computador en inglés imprime $1,234,567.89. Si necesitas un formato fijo, pásalo como primer argumento: String.format(Locale.US, "%,.2f", x). Las pruebas del ejercicio 4.10 fijan el formato colombiano por su cuenta, así que tú no tienes que pasar ningún Locale.

Pregunta rápida

¿Qué produce String.format("[%-6s]", "sol")?

El 6 es el ancho total y el - alinea a la izquierda, así que se rellena con 3 espacios a la derecha. Sin el -, los espacios irían a la izquierda.

Cosas para recordar

  • Variables locales y referencias en el Stack; objetos en el Heap. get da una referencia, no una copia.
  • Integer, Double y String son inmutables: se reemplazan, no se modifican.
  • Un for-each es un Iterator escondido. Para borrar mientras recorres, borra a través de él.
  • La variable decide qué métodos puedes llamar; el objeto decide qué código corre.
  • Un tipo nuevo debería ser una clase nueva, no un else if nuevo en todas partes.
  • Hay fugas de salida (getters) y de entrada (constructores). Una copia defensiva cierra las dos.
  • printf imprime, String.format devuelve. Dentro de una clase, casi siempre el segundo.

¿Y cuándo gana el arreglo?

Una List<Double> guarda referencias a objetos Double, cada uno con su cabecera de objeto; un double[] guarda los números seguidos, 8 bytes cada uno. La diferencia es de unas 3 a 4 veces más memoria para la lista, más el trabajo extra del recolector de basura, más alguna ampliación en un momento que tú no eliges. En un programa de gestión eso no se nota. En software embebido, control industrial o procesamiento de señales en tiempo real (miles de muestras por segundo, memoria escasa, tiempos de respuesta garantizados) sí, y ahí el arreglo de primitivos de tamaño fijo sigue siendo la herramienta correcta.

Dos herramientas que ayudan

El depurador de tu editor (VS Code, IntelliJ, Eclipse): pon un punto de interrupción, despliega una variable ArrayList y verás por dentro su size y su elementData, con las casillas de sobra en null. Es la sección 2.6 en vivo. SonarLint (o SonarQube for IDE): un complemento que revisa tu código mientras escribes y te avisa, entre muchas otras cosas, cuando un getter entrega una colección interna sin copiarla.
