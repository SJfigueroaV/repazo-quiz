Parte 3

Diseño con colecciones

Ya sabes usar listas. Esta parte es sobre diseñar con ellas: dónde vive la lista, quién puede tocarla, qué significa que dos objetos sean "el mismo", y cómo se migra código viejo. Termina con el sistema de urgencias completo, construido por pedazos.

Al terminar esta parte

  • Guardas una lista dentro de una clase sin dejar que nadie la modifique por la espalda.
  • Escribes equals y hashCode, y sabes qué métodos de la lista dependen de ellos.
  • Eliges el elemento más prioritario de una lista, con empates y listas vacías resueltos.
  • Migras una clase de arreglo fijo a lista sin cambiarle la cara al resto del programa.
  • Construyes un sistema completo: la sala de urgencias con triage.

3.1 Una clase que guarda una lista

Hasta ahora las listas andaban sueltas: se creaban en un método y se pasaban de un lado a otro. En un programa de verdad la lista casi siempre vive dentro de una clase que la cuida: un Equipo con sus jugadores, un Carrito con sus productos, una SalaUrgencias con sus pacientes. Esa clase es la dueña, y es la única que debería poder cambiarla.

El problema aparece cuando alguien pide ver el contenido. La forma obvia tiene una fuga:

EquipoAbierto.java
public class EquipoAbierto {
    private List<Jugador> jugadores = new ArrayList<>();

    public void fichar(Jugador j) { jugadores.add(j); }
    public int cantidad()         { return jugadores.size(); }

    public List<Jugador> getJugadores() {
        return jugadores;      // ← entrega la lista interna, tal cual
    }
}

El atributo es private, sí, pero el método regala una referencia a la lista de adentro. Quien la reciba puede hacerle lo que quiera:

abierto.getJugadores().clear();   // acabo de despedir a todo el equipo desde afuera

salida

Jugadores: 2 Después de que alguien llamó clear(): 0 El equipo cerrado no deja: UnsupportedOperationException Jugadores del equipo cerrado: 2

Hay dos formas de cerrar la fuga, y las dos son válidas:

// Opción A: devolver una copia. Quien la reciba puede modificarla,
// pero está modificando SU lista, no la del equipo.
public List<Jugador> getJugadores() {
    return new ArrayList<>(jugadores);
}

// Opción B: devolver una vista de solo lectura. Si intentan modificarla,
// reciben UnsupportedOperationException (requiere import java.util.Collections).
public List<Jugador> getJugadores() {
    return Collections.unmodifiableList(jugadores);
}

¿Cuál de las dos?

La copia es más simple de explicar y cuesta O(n). La vista no copia nada y además avisa con una excepción cuando alguien intenta modificarla, lo cual delata el error en vez de esconderlo. Ojo con un detalle: la vista sigue reflejando los cambios que haga el equipo por dentro, y la copia no.

Fíjate que ninguna de las dos protege a los Jugador en sí: quien reciba la lista puede pedirle sus datos a cada jugador, y si la clase Jugador tuviera setters, podría cambiarlos. Por eso los objetos que se guardan en colecciones suelen tener sus atributos privados y pocos (o ningún) setter.

Pregunta rápida

¿Por qué no basta con declarar private List<Jugador> jugadores;?

private impide que alguien escriba equipo.jugadores = otraLista, pero si un método entrega la referencia, el objeto lista queda expuesto y se le puede llamar add o clear. final tampoco ayuda: también protege la variable, no el contenido.

3.2 Cuándo dos objetos son "el mismo"

En esta sección

  • Cierras el asunto que quedó abierto en la Parte 2: contains con objetos propios.
  • Escribes equals siguiendo el molde, y entiendes por qué hashCode viene con él.

En la Parte 2 viste que contains decía false aunque la lista tuviera un producto con los mismos datos. La razón: contains, indexOf y remove(Object) preguntan equals, y el equals que se hereda de Object compara identidad, o sea "¿son el mismo objeto en memoria?".

Para que Java sepa qué significa "igual" en tu dominio, se lo dices tú. El molde es siempre el mismo:

@Override
public boolean equals(Object obj) {
    if (this == obj) {
        return true;                       // 1. el mismo objeto
    }
    if (obj == null || getClass() != obj.getClass()) {
        return false;                      // 2. null u otra clase
    }
    Producto otro = (Producto) obj;        // 3. ahora sí puedo tratarlo como Producto
    return sku.equals(otro.sku);           // 4. comparo lo que identifica al objeto
}

Fíjate en el paso 4: un producto no se identifica por su nombre ni por su precio, sino por su SKU. Igual que una persona se identifica por su cédula y un libro por su ISBN. Elegir ese campo es la decisión de diseño; el resto es el molde.

Si escribes equals, escribe hashCode

Es una regla del lenguaje: dos objetos iguales deben devolver el mismo hashCode. Si no la cumples, tu clase funcionará en listas pero se comportará de forma errática en estructuras que usan el hash, como HashMap o HashSet (guardas algo y no aparece al buscarlo). Lo normal es delegar en el mismo campo: return sku.hashCode();

Pregunta rápida

Tu Producto ya tiene equals por SKU. ¿Qué hace lista.remove(new Producto("P01", "otro nombre", 0.0))?

remove(Object) recorre la lista preguntando equals. Como tu equals solo mira el SKU, encuentra el producto P01 y lo borra, sin importar el nombre ni el precio del objeto que le pasaste. Por eso vale la pena pensar bien qué campo identifica al objeto.

3.3 Elegir un elemento: mínimos, empates y listas vacías

"El más barato", "el más crítico", "el que llegó primero". Este patrón aparece en todos los sistemas y tiene tres decisiones escondidas que conviene tomar a propósito:

public static Producto masBarato(List<Producto> productos) {
    if (productos.isEmpty()) {
        return null;                       // 1. ¿qué pasa si la lista está vacía?
    }

    Producto masBarato = productos.get(0); // 2. arranco con un candidato de verdad

    for (Producto producto : productos) {
        if (producto.getPrecio() < masBarato.getPrecio()) {   // 3. ¿< o <=?
            masBarato = producto;
        }
    }
    return masBarato;
}
  1. La lista vacía. No hay respuesta correcta universal: puedes devolver null, lanzar una excepción o devolver un Optional. Lo que no puedes es ignorar el caso, porque get(0) sobre una lista vacía lanza IndexOutOfBoundsException.
  2. El candidato inicial. Empieza con el primer elemento real, no con un valor inventado como Double.MAX_VALUE. Es el mismo error del ejercicio 1.2 con int mayor = 0.
  3. El empate. Con <, el primero que encontraste se queda con el puesto; con <=, lo desplaza el último. Un solo carácter decide a quién atienden primero, y en el proyecto de esta parte esa diferencia significa qué paciente pasa antes a consulta.

3.4 Migrar de arreglo fijo a lista

En esta sección

  • Ves lado a lado el mismo método escrito con arreglo y con lista.
  • Entiendes por qué un arreglo fijo en el lugar equivocado tumba un sistema.

Hay una historia que se cuenta en clase y que resume esta parte. Una tienda en línea implementó el carrito de compras así:

public class CarritoLegacy {
    private Producto[] items = new Producto[10];   // tamaño fijo de 10 productos
    private int contador = 0;

    public void agregar(Producto p) {
        items[contador] = p;                        // ¡la línea de la tragedia!
        contador++;
    }
}

Funcionó durante meses. La noche del CyberMonday, el primer cliente que armó un combo de 11 productos reventó su sesión, y detrás de él, miles:

salida

Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 10 out of bounds for length 10

El número 10 no fue una decisión técnica, fue una suposición sobre el mundo: "nadie compra más de 10 cosas". Los arreglos fijos obligan a hacer esa suposición; las listas, no. Por eso la regla práctica es: si la cantidad de elementos la decide el usuario en tiempo de ejecución (un carrito, una sala de espera, una lista de transacciones), no uses un arreglo fijo.

Migrar no es reescribir el programa: es cambiar el atributo y ajustar los métodos que lo tocaban. La firma pública se conserva, así que el resto del código sigue igual. Este es el antes y después del método más feo, eliminar por ISBN en una biblioteca:

// ANTES: arreglo fijo, contador manual y shifting
public boolean eliminarLibro(String isbn) {
    for (int i = 0; i < cantidadLibros; i++) {
        if (estanteria[i] != null && estanteria[i].getIsbn().equals(isbn)) {
            for (int j = i; j < cantidadLibros - 1; j++) {
                estanteria[j] = estanteria[j + 1];
            }
            estanteria[cantidadLibros - 1] = null;
            cantidadLibros--;
            return true;
        }
    }
    return false;
}

// DESPUÉS: la lista se compacta sola
public boolean eliminarLibro(String isbn) {
    return estanteria.removeIf(libro -> libro.getIsbn().equals(isbn));
}

Trece líneas contra una. Y desaparecen de un golpe tres fuentes de errores: los índices del shifting, el contador que hay que mantener sincronizado y las casillas null que había que validar.

3.5 Proyecto: la sala de urgencias

Lo que sigue es un sistema completo, construido en seis ejercicios encadenados. Cada uno agrega un método a la clase SalaUrgencias, y las plantillas ya traen resueltos los métodos de los ejercicios anteriores, así que si uno se te atraviesa puedes seguir con el siguiente.

El dominio. En urgencias no se atiende por orden de llegada, se atiende por triage: una clasificación de 1 a 5 donde 1 es lo más grave (paro cardíaco, emergencia vital) y 5 lo más leve (cita menor). Entre dos pacientes con el mismo triage, pasa primero el que llegó antes. Esa regla, "el número más bajo gana, y el empate lo rompe la hora de llegada", es el corazón del sistema.

3.6 Cierre: qué estructura elegir

Después de tres partes, la decisión se reduce a unas pocas preguntas:

Si…Usa
Sabes exactamente cuántos elementos hay y no cambiaUn arreglo (Tipo[])
La cantidad la decide el usuario o el programa en ejecuciónList con ArrayList
Consultas mucho por posiciónArrayList (get es inmediato)
Insertas y borras mucho por el medioLinkedList (o repensar el diseño)
Buscas por una clave (cédula, SKU, ISBN)HashMap — el tema que sigue

Cosas para recordar

  • La lista vive dentro de la clase que la cuida; hacia afuera se entrega una copia o una vista.
  • private protege la variable, no el objeto al que apunta.
  • contains, indexOf y remove(Object) dependen de tu equals.
  • Si escribes equals, escribe hashCode.
  • Al elegir un elemento, decide a propósito qué pasa con la lista vacía y con los empates.
  • Valida en el constructor: un objeto que no puede existir en mal estado simplifica todo lo demás.
  • Un método que se apoya en otros métodos de su propia clase casi siempre está mejor escrito.

Y con eso terminaste el curso. Si quieres seguir, el paso natural es HashMap (buscar por clave en vez de recorrer), Comparable y Collections.sort (ordenar listas de tus objetos), y los streams de Java 8, que convierten los recorridos de filtrar y sumar que escribiste aquí en una sola línea.
